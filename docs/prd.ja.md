# itoc 製品要求仕様書

## 概要

`itoc` は、意図を表す成果物と実装成果物の関係を発見し、維持するための専用ツールである。名前には `ito`（意図。日本語の「糸」も想起させる）と code を組み合わせ、「ito to code」「ito + code」の意味を込めている。ソフトウェア開発全般にあるトレーサビリティの課題に取り組む。

## 解決する課題

開発ツールはsemantic pathからコードを解決するためにAIによる探索を使う場合がある。非決定論的なAIの推論だけに頼ると、関連コードをどのように見つけたかを再現、説明し、一貫して再利用することが難しい。AIの支援は有用だが、それだけでは不確実性や探索の繰り返しが多く残る。

開発者は、文書や機能に対応する実装、テスト、関連成果物をしばしば再構成しなければならない。この作業は繰り返し発生する隠れたコストであり、関係を記録し、回復する有効な方法は広く確立されていない。

Reverse workflowでは既存コードから意図をたどる必要があり、この必要性がさらに高まる。あるコード成果物から関連する別のコードを見つけ、その関係をsemantic情報の抽出に役立てる場合もある。信頼できる関係探索は、Forward開発とReverse workflowの両方を支えられる。

## 製品の方向性

`itoc` は、再現可能な証拠とAIの支援を組み合わせ、成果物間の関係を発見しやすくする。決定論的な手法でGit履歴、変更されたpath、差分、リポジトリ構造などの証拠を使い、候補を特定・順位づけする。結果には根拠を示し、不確実性を明らかにする。AIは曖昧な証拠の解釈、候補探索の拡張、関係の要約を補助できるが、再現可能な手法に取って代わるものではない。

証拠が十分でない限り、関連づけは候補として扱う。たとえば、二つの成果物が同じcommitに含まれることは有用な証拠だが、それだけで意味上の関係が証明されるわけではない。

## 初期目標

Forward開発から始める。文書がcommitされたとき、その内容とGit履歴を使って、文書に関連する実装コードを見つける。候補となるコード成果物と、それぞれの関係を支える履歴その他の証拠を提示する。

初期スコープはGitに基づく探索に絞る。Git上の証拠には、文書とコードが同じcommitで変更されたことだけでなく、既存文書を後続commitで変更した履歴、繰り返される共変更、差分、作業者や時系列のパターン、利用可能な場合は作業項目の文脈も含められる。commit messageの情報量が少なくても、これらの手掛かりは利用できる。証拠が繰り返されれば候補を強められるが、単一のシグナルを証明とはみなさない。

成果物の所在を特定することと、その意図を理解することは分けて扱う。初期目標は主に実装候補の所在を特定することにある。コードが何を実現し、どの意図を担うかという深い解釈は、特にReverse Syncで必要となる、より広い課題である。リポジトリの証拠が不十分な場合は、不確実性を残さなければならない。

初期実装はGit共変更探索と、決定論的な文書参照探索の両方をサポートする。文書探索はMarkdown/MDXとreStructuredTextから始め、明示的なローカルリンク、インラインコード/literal、強調語を抽出し、パス・ファイル名・ソース本文の文字どおりの一致を探す。意味上の言い換えは推論しない。方式は個別に選択でき、形式別extractorで拡張できるようにし、各結果の根拠を保持する。確認済みの関係を将来保存し、ForwardとReverseの作業で再利用する可能性がある。永続化、鮮度の維持、分割・統合への対応は未決の設計課題である。Gitに基づく探索では、削除された入力pathを対象外とする。対象が移動または改名された場合は、現在の移動先を起点に履歴をたどって探索を続ける。

## ノイズと証拠の品質

実装候補からテスト候補を探す方法として、シンボル名、ファイル名、Gitの共変更をそれぞれ別の根拠として評価する。シンボル名がテキスト中に現れたことは、参照先が解決されたことや、テストがその実装を検証していることの証明ではない。文書の手掛かりについても、一致の種類と頻度に応じた順位付けを、根拠を残しながら評価する。頻出語という理由だけで候補を除外せず、重みは仮定で固定せずに評価を通じて決める。[検証計画](discovery-evaluation.ja.md)に実験案をまとめる。テスト探索は初期実装があり、文書の手掛かりの順位付けは今後の検討方針である。将来的には言語を考慮した探索の精度向上も検討する。

Git履歴には、意味上の関係を見えにくくする変更が含まれる。たとえば、linterやformatterの一括適用、パッケージ更新、ファイルの改名・移動だけを行うリファクタリングがある。こうした変更と、意図を表現または実装する変更を見分けることは、製品上の重要な課題である。

commitメッセージやコメント、変更の形、ファイル移動、その他のリポジトリ上の証拠を手掛かりとして検討する。変更がノイズかどうかの分類にJevを使う可能性も探る。分類方法は未決定であり、利用者が判断を確認できるよう、ツールはその根拠を保持する。

## 将来の方向性

Reverse workflowでは、`itoc` はコードを起点に関連するコード成果物を発見し、その証拠からsemantic情報を抽出する支援にも使える可能性がある。将来的には、文書、ソースコード、テスト、決定記録などの開発成果物を、ForwardとReverseの両方で扱う関係モデルを目指す。

## 原則

- 候補発見には、再現可能で確認できる証拠を優先する。
- AIは不確実または解釈を要する作業を補助し、唯一の探索手段とはしない。
- 成果物が選ばれた理由と、残る不確実性を示す。
- Git上の共変更などのシグナルは証拠として扱い、意味上の関係を自動的に証明するものとはみなさない。
- 対象をForwardの小さなワークフローに絞って始め、その結果を拡張の指針にする。
