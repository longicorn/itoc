# ADR: キーワード検索の開始候補

## 状態

方向性は合意済み。検索と絞り込みの詳細は未決。CLIの仮の入口はあるが、検索は実装されていない。

## 背景

利用者が機能名や画面の表示文言を知っていても、リポジトリ内のパスが分からない場合がある。キーワード検索は探索を始める候補を提供する。一致は確認のための根拠であり、そのファイルが目的の機能を説明または実装している証明ではない。一致しなくても、関連する成果物が存在しないとは限らない。

## 決定

- 明示的に指定されたキーワードを受け取り、何がどこで一致したかを示す根拠とともにリポジトリ内のパス候補を返す。
- パスは探索の開始候補として扱う。その先の関係探索は[discovery](../discovery.ja.md)が担い、どの候補を調査または採用するかは利用者や呼び出し元のワークフローが選ぶ。
- CLIは `itoc [options] <file-path>` に加え、キーワード用に `itoc [options] --search <keyword>` を案とする。明示的に選択することで、存在しないパスをキーワードと誤解釈することを避ける。仮の入口は検索が未実装であることを表示し、discoveryやスコア計算を呼び出さない。

## 影響と検討案

初期案として、grepのようにファイル内容を文字列検索し、あわせてファイル一覧を絞るようにリポジトリ内のパスとキーワードを照合する方法を評価する。内容とパスの一致を別々の根拠として示し、それぞれの有用性を評価できるようにする。これは検討案であり、特定のコマンドや検索設計全体を決定するものではない。開始候補をさらに絞り込み、選択する方法は未決である。

文字列の一致は確認しやすい一方、別の表現を見逃したり、無関係な結果を含んだりする。候補の選択とassessmentの対象範囲の判断は別に扱う。

## 未決事項

- どのファイルや箇所を検索し、どの根拠を表示するか。
- 複数の候補をどう絞り込み、選択してdiscoveryに渡すか。
- 一般的な語や曖昧な語の一致をどう順位付け・絞り込みするか。具体例を使って方法や重みを評価する。
- 空または不正な入力、一致がない検索をどう報告するか。
- どの実装手法を使い、構想中の `keyword.go` とどう関連付けるか。

既存の候補出力はスコアやGitの共変更根拠を前提とする。仮実装は独立した応答を返し、検索済みで一致がなかったかのように見せない。結果モデル、出力形式、discoveryへの接続は検索実装時に設計する。
