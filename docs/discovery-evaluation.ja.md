# 探索改善の検証

## 目的

テスト探索と文書の手掛かりの順位付けを改善する前に、手法を評価する。アルゴリズム、重み、閾値、既定値は評価結果を踏まえて決める。結果は根拠のある候補であり、意味上の関係が確定したものではない。再現性は正確性を保証しない。

## 実装候補からテスト候補を探す

発見済みの実装ファイルを起点に、識別子の一致、ファイルの命名と配置、実装とテストのGit共変更を別々の根拠として比較する。候補ごとに起点となった実装と根拠を残す。重複候補を統合する際も根拠を失わない。別の候補から導いたテストには、独立した探索方法の一致ボーナスを自動的に適用しない。連鎖的な拡大を避けるため、実装候補から一段だけ探索する。

Universal Ctagsで実装ファイルの定義を抽出し、その識別子をテストファイルから探す方法を試す。定義とテスト側の一致箇所を記録し、文字列の一致と参照先が解決された結果を区別する。同名や汎用的な名前、コメント、言語固有の構文、間接呼び出しによる影響を確認する。ctagsの有無とバージョン、対応言語、未導入や失敗時の扱いを記録する。GNU Globalへの対応は今回の試行では見送る。命名規則は言語ごとに評価し、Git履歴では削除・改名されたファイルや一括変更も考慮する。

各手法を単独と組み合わせの両方で比較する。名前が対応するテスト、異なるテスト、共通テスト、似た名前の無関係なテスト、対応テストが存在しない実装を含める。フィルタ、ノイズ閾値、件数制限、スコアが起点の実装と導出されたテストの双方にどう影響するかを確認する。処理順序はスコアの継承を前提にせず、結果を踏まえて決める。

## 文書の手掛かりの順位付け

一致の種類、文書中の位置、候補、一致した語が索引内の何ファイルに現れるかを記録する。少なくとも既存ファイルへの明示的なパス、ファイル名の完全一致、ファイル名の部分一致、ソース本文の一致を区別する。頻出語の寄与を下げる方法を比較するが、頻度だけを理由に候補を除外しない。同じ手掛かりの繰り返しが無制限に加点されないようにし、異なる複数の手掛かりによる加点の上限も評価する。明示的なパスは参照の根拠であり、実装関係の証明ではない。

まず文書探索単体で、現行の順位と提案する順位を比較する。その後、Gitのスコア、探索方法の一致ボーナス、ノイズ判定、フィルタとの相互作用を評価する。数値の重みや閾値は評価結果が得られるまで固定しない。

## 検証手順

1. 複数のリポジトリと論理対象を選ぶ。履歴の豊富な文書、履歴の少ない文書、明示的な参照を含む文書を対象にする。候補にはDiscourse（Rails）、Wagtail（Django）、Spinel（C）があり、NagiのRunner文書も初期の検証対象とする。
2. リビジョン、入力、ツールのバージョン、設定、索引の範囲と除外対象を記録する。`--limit 0`でもノイズフィルタは無効にならない。使用できなかった方法、エラー、索引の鮮度も記録する。
3. 関連する実装とテストの候補を人手で確認し、判断理由と不明な項目を残す。AIの出力は確認の参考にはできるが、正解集合とはしない。無関係な例と既知の見落としも含める。
4. 現行方式と提案方式を単独および組み合わせて比較する。見つかった関連候補、見落とし、無関係な候補、順位、根拠、実行時間を記録する。具体例と未解決の判断を残し、結果を実装範囲や既定値の選択に使う。

初期の2ファイルずつの実行可能性確認では、導入済みのUniversal CtagsはRuby、Python、Cの定義例を抽出できた。導入済みのGNU Globalの既定設定はCの例を索引化したが、RubyとPythonの例は索引化しなかった。これはリポジトリ全体での精度や性能の評価ではない。
