# ADR: CLIのワークフロー調整

## 状態

現在の実装方針。キーワード検索は実験段階であり、複数の探索方式を組み合わせる際のスコアは暫定的である。

## 背景

[CLIの要件](prd.ja.md)は、リポジトリ内の成果物を探索し確認するための共通の入口を求めている。探索結果は関係が確定したものではなく、根拠を伴う候補である。利用者は探索方式を選び、ノイズを減らし、確認する詳細の量を選ぶ必要がある。探索方式ごとに独自のインターフェースを実装する必要はない。

## 決定

- CLIは入力を検証し、探索、任意のテスト候補の展開、候補の準備、出力を調整する。各処理の具体的な動作は[探索](../discovery/prd.ja.md)、[フィルター](../filter.ja.md)、[出力](../output.ja.md)に委ねる。
- 起点にはリポジトリ内のファイルパスを1つ受け付けるか、`--search`でキーワードを明示的に指定する。存在しないパスをキーワードと推測しない。検索との接続は実験段階であり、選択方法と未解決事項は[キーワード検索のADR](../keyword/adr.ja.md)に記録する。
- 探索方式を明示的に選択できるようにし、既定はGitとする。複数の方式を選んだ場合は並行して実行し、根拠を保持しながらパスごとに候補を統合する。追加の方式が同じ候補を見つけるたびに1点を加える現在の処理は暫定的であり、関係を確定するものではない。
- テスト候補の展開は既定で有効にし、無効化できるようにする。繰り返し指定できる候補フィルターと、ノイズ、最低スコア、グループごとの結果件数の設定を用意する。最低スコアによる絞り込みを件数制限より先に適用する。
- 既定ではテキスト形式、指定時にはJSON形式で出力し、詳細な根拠はverboseオプションで確認できるようにする。結果は標準出力、警告、選択の案内、エラーは標準エラーに出す。不正な入力や処理エラーは失敗の終了ステータスを返す。

## 影響

共通のワークフローにより、各方式の結果を一貫した方法で絞り込み、表示できる。根拠も残るため、人が候補を評価できる。並行して実行する方式は互いを補う手掛かりを提供できるが、一致の背景に共通する根拠がある可能性もある。スコアの加点は評価が必要である。テスト候補の展開は外部ツールに依存する場合があり、ctagsがない場合は警告を出して識別子による展開を省略する。

## 未解決事項

- 探索方式間の一致をどのように評価し、重み付けするか。
- キーワード検索の実験を進める中で、候補をどのように選択して探索に渡すか。
- 候補の見落としと確認作業の負担を釣り合わせるには、どの既定値と設定が適切か。
