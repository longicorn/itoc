# ADR: 候補の出力と責務の境界

## 状態

現在の実装方針。出力形式と今後の変更は引き続き評価する。

## 背景とインターフェース

[フィルター](../filter/adr.ja.md)は、分析済みの候補を表示用に選別し、並べ替え、件数を制限する。出力は探索の生データではなく、その結果の`[]candidate`を受け取る。各候補にはパス、スコア、分類、ノイズ情報、根拠が含まれる。これらは判断の手がかりであり、関係の証明ではない。

現在の整形インターフェースは`renderCandidatesWithEvidence([]candidate, format, showEvidence) ([]byte, error)`である。CLIが形式と詳細な根拠の表示有無を選び、整形処理を呼び出して、返されたバイト列を書き出す。`renderCandidates`は根拠を非表示にして同じ処理を呼ぶ。候補の選別と順序付けはフィルター、スコア付けと分類は分析の責務であり、出力はこれらを行わない。

## 決定と現在の動作

準備済みの候補を、人向けのテキストまたは後続ツール向けのJSONに整形する。候補の確認に必要な情報を示し、要求に応じて詳細な根拠を表示する。CLIはオプションの解析と書き出しを、出力は表示形式を担当する。

テキストでは候補を実装、テスト、文書の順に見出しで分け、各グループ内では入力順を保つ。各候補のパス、スコア、ノイズスコア、共変更commit数、パスボーナスを示し、ノイズ用語があれば併記する。詳細な根拠は要求時に表示する。候補が空の場合は`No code candidates found.`と表示する。

JSONでは入力順の配列を返す。各レコードに`path`、`score`、`co_changed_commits`、`filename_bonus`、`kind`、`noise_score`を含める。ノイズ用語があれば`noise_terms`を含め、詳細な根拠が要求され存在する場合は`evidence`を含める。テストらしい候補の`kind`は`test`となる。候補が空の場合は空配列を返す。現在CLIは整形結果を標準出力に書き、ファイル出力は未実装である。

## 影響と未解決の課題

共通の整形境界により、選別規則と表示形式を独立させられる。テキストはグループ間の全体順序を変えるが、JSONはフィルターの順序を保つ。表示されるスコア、分類、根拠はいずれも発見的なものであり、人による判断が必要である。

候補の項目や根拠が変化する際、JSONの互換性をどう管理するか。利用者には、どのような出力形式や根拠の表現がさらに役立つか。
