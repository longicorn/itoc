# ADR: 候補フィルターの境界

## 状態

現行の実装方針。既定値とフィルター規則は引き続き評価する。

## 背景とインターフェース

[フィルターのPRD](prd.ja.md)は、探索された候補を表示用に選別し、順位付けすることを求めている。discoveryが根拠を収集し、[analysis](../analysis/adr.ja.md)がスコア付けと分類を行う。分析後、複数の探索手法の結果を統合し、必要に応じてテスト探索で候補を追加する。filterは生の探索根拠ではなく、その結果の候補を出力前に受け取る。[discoveryのADR](../discovery/adr.ja.md)も参照。

現在のインターフェースは`prepareCandidates([]candidate, candidateOptions) []candidate`である。各候補はリポジトリ相対パス、スコア、分類、ノイズスコア、根拠を持ち、オプションは選択条件と件数制限を指定する。戻り値は、表示用に選択し順序付けた候補のスライスである。filterはこれらのフィールドを使うが、スコアや分類の計算、根拠の解釈、関係の正否の判定は行わない。

## 決定: filterの責務

探索手法に依存しない共通の候補準備段階を設ける。利用者の選択・除外条件を適用してノイズを減らし、残った候補を順位付けしてグループごとの表示件数を制限する。利用者が候補を判断できるよう、選択した候補の根拠を出力に残す。オプションの解析と検証はCLI、表示はoutputの責務とする。

## 現在の動作

1. 拡張子とパスによる包含・除外を適用し、続いて候補またはグループを明示的に除外する。
2. `--show-noisy`が指定されていなければ、最大ノイズスコアを超える候補を除外する。最低スコアが0より大きい場合は、それ未満の候補も除外する。
3. スコアの降順、同点の場合はパスの昇順に並べ、グループごとの件数制限を適用する。テストと判定された候補は独立したグループとし、それ以外は分類を使う。先に並べることで、各グループの上位候補を残す。

CLIの既定値は最大ノイズスコア1、最低スコア0、グループごとの上限10件である。上限0は無制限を意味する。通常のパスパターンはリポジトリ相対パスの部分文字列に一致する。globのメタ文字を含むパターンは`filepath.Match`でパス全体に照合し、`*`は`/`をまたがない。拡張子は小文字にして比較する。明示的な除外にはグループ名または正規化したリポジトリ相対パスの完全一致を使う。

## 帰結と未解決の問い

共通の処理順により、探索手法を通じて選別方法が統一され、順序を再現できる。一方、しきい値と件数制限は関連する候補を隠すことがあり、その有用性はヒューリスティックなスコアと分類に左右される。利用者はしきい値を調整し、ノイズの多い候補を含め、件数制限を解除できるが、根拠の判断は必要である。

既定値、照合規則、グループごとの上限を、見逃した候補と確認作業の量に照らしてどう評価するか。探索元や分析の変更に合わせて、候補とオプションのインターフェースをどう発展させるか。
