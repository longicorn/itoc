# ADR: 根拠に基づく成果物間の関係探索

## 状態

方向性は合意済み。実装の詳細は未決。

## 背景

`itoc`は、意図を表す成果物と実装成果物の関係を発見し、再利用しやすくすることを目指す。開発ツールではsemantic pathからコードを解決する際にAIによる探索へ依存する場合がある。AIは曖昧な証拠の解釈に役立つ一方、AIだけに頼ると、探索の再現、説明、一貫した再利用が難しい。

初期ユースケースはForward開発である。commit済みの文書とリポジトリ履歴を使い、実装候補を見つける。関連成果物の所在を特定することと、その意図を理解することは別の課題である。このADRは候補発見を扱い、意味を完全に解釈する仕組みまでは定めない。

Git履歴には、共変更、既存文書への後続変更、繰り返される変更パターン、差分、変更path、作業者、時系列、利用可能な作業項目の文脈など、観測可能な証拠がある。branch、PR、mergeの文脈も手掛かりになり得る。同じbranchやPRにまとめられた変更が関連する場合や、bugの根本原因に対処する修正、付随する小さなbugfixが含まれる場合がある。こうしたまとまりは関係性の可能性を高めることはあっても、それだけで関係を確定するものではない。

履歴には、formatterの一括適用、依存関係の更新、renameだけのリファクタリングなどのノイズも含まれる。commit messageの情報量が少ないことや、一つのcommitまたはPRに無関係な作業が混在することもある。そのため、候補の根拠と不確実性を保持する必要がある。

## 現在の探索方針

探索の入口はリポジトリ内のパス、または機能名や画面の表示文言などのキーワードとする。Nagiではsemantic pathを文書パスに解決してから`itoc`に渡す。結果は根拠付きの候補であり、assessmentなどの用途に採用するかは利用側が判断する。文字列の一致、共変更、呼び出しの到達可能性だけでは、実装やテストの関係は確定しない。

入口候補を見つけ、そこから関係をたどって別の成果物を探す。静的な呼び出し関係は根拠の一つだが、到達可能性だけで機能の範囲は決まらない。文字列一致、構文上の呼び出し、静的に参照先を解決した呼び出しを区別し、未解決の関係や解析の限界を示す。当面は導入しやすい外部ツールやライブラリによる静的解析を検討する。ツールの選定と対応言語は未決である。動的観測は将来の可能性であり、現在の実装方針には含めない。

対象を定義・説明する文書、振る舞いや制約を担う実装、それらを検証するテストを候補として探す。上位文書や共有コードを含めるかは用途によって異なり、未決である。順位付けの目的、スコア、重み、見落としと無関係な候補のバランスは、具体例と評価を通じて決める。実装は経験を積みながら段階的に修正する。

## 従来のGit中心の決定

以下は初期の方向性とCLIに関する決定の記録である。上記の探索方針はcommit済み文書やGit履歴に限定されない。具体的なGitシグナルや変更のまとまりの扱いには、引き続き実装と評価が必要である。

## 決定

- `itoc`の実装言語にGoを採用する。独自のディレクトリ構成は設けず、一般的なGoプロジェクトの慣例に従う。
- 初期構成は最小限の実行可能なGo moduleとする。リポジトリのルートにコマンドのエントリーポイントを置き、`go.mod`でmoduleを宣言する。実装上の必要が生じるまでは、追加のpackageや依存関係を設けない。
- commit済み文書に対する実装候補のForward探索から始め、再現可能な主要証拠としてGit履歴を使う。
- 初期CLIではリポジトリ内のファイルpathを引数として受け取り、そのファイルのGit履歴から関連しそうな実装コードファイルを特定・順位づけする。出力は証拠に基づく候補であり、意味上の関係が確定したという主張ではない。
- 対象文書の最初のcommitを含むbranch/PRの変更まとまりを、最初の探索単位とする。その文書が後続のbranch/PRのまとまりでも変更されていれば、後続のまとまりも探索単位として順に処理する。各まとまりの中では共変更、後続変更、差分を優先する。まとまりは探索順と証拠の文脈を定めるものであり、意味上の関係を確定するものではない。
- 利用可能な場合は、共変更とその反復、後続の変更、差分とpath、作業者と時系列、作業項目の文脈、branch/PR/mergeのまとまりを組み合わせる。
- 各シグナルは候補の関係性を高めたり下げたりする証拠として扱い、意味上の関係の証明とはみなさない。特に、同じcommit、branch、PR、mergeに含まれるだけでは関係を確定しない。
- 人が候補を判断できるよう、裏付けとなる証拠と残る不確実性を提示する。
- Git履歴に加え、リポジトリ相対path全体のtoken類似度を控えめな順位づけのシグナルとして使い、その加点を個別に表示する。共通のproject rootは除外する。拡張子やbasenameが異なる文書とコード（例：`users/prd.md`と`users/users.go`）もpath要素の一致で結びつけられる。pathの類似だけで関係を確定しない。
- 言語ごとの一般的なファイル名prefix/suffixとdirectory規則からテストらしいファイルを判定する。拡張子を除いたstemに命名markerを適用する（例：`_spec.rb`、`_test.go`）。候補からは除外せず、分類して実装候補の後に別表示する。この判定はヒューリスティックであり、確定的な分類として扱わない。
- 文書だけでなくコードファイルも入力可能にする。関連する文書ファイルも候補に含め、別グループで表示する。
- 候補のノイズを抑えるため、拡張子とリポジトリ相対pathに対するinclude/exclude指定を複数回指定可能にする。globの照合規則を定義してヘルプに示す。
- path filterは、通常文字列ならリポジトリ相対pathの部分一致、glob記号を含むpatternならpath全体との照合とする。
- `--include-path`と`--exclude-path`は、glob記号を含まない通常文字列ならリポジトリ相対pathの部分一致とする。glob記号を含むpatternはpath全体に照合する。
- 初期表示は各グループの上位10件に制限する。CLIで件数を変更でき、明示的に無制限にもできる。
- groupごとの件数limitに加えて最低scoreを指定可能にし、scoreで絞った後にlimitを適用する。
- 既知のノイズ候補を減らすため、`implementation`・`document`・`test`のgroup全体、またはrepository-relative path完全一致による個別候補の非表示指定を複数回受け付ける。
- commit message中の`lint`、`linter`、`format`、`formatter`、`refactor`、`refactoring`などからnoise scoreを独立して記録する。現段階では候補scoreに合算せず、順位づけやfilterにも使わない。将来の評価に向けた証拠として表示する。
- 初期表示は各グループの上位10件に制限する。CLIで件数を変更でき、明示的に無制限にもできる。通常の出力を確認しやすくしつつ、必要時は全候補を調べられるようにする。
- AIは解釈、候補探索の拡張、要約を助ける任意の補助手段とし、再現可能な証拠に基づく探索の代わりにはしない。
- Jevによるノイズ分類は初期スコープから後回しにする。AI/LLMによる支援は解釈を補う任意機能とし、利用者が選択できるようにする。再現可能な証拠に基づく探索の代わりにはしない。
- 結果は標準出力に出し、出力形式と出力ファイルをオプションで指定可能にする。
- まず自プロダクトで評価し、ツールが動作してきた段階で公開OSSに広げる。候補の関連性は人が最終確認する。
- 成果物の所在特定と、コードの意図を深く理解することを区別する。初期目標は主に候補の所在特定とし、証拠が足りない場合は不確実性を明示する。

## 影響

複数種類の証拠や反復する証拠を使うことで、commit messageの情報量が少ない場合も候補の順位づけを改善できる可能性がある。branch、PR、mergeのメタデータは、関連するbug修正や付随する変更の文脈を補える。一方、大きな変更や付随的な修正は誤った関連づけを生むこともあるため、まとまりを確定的なリンクに変換してはならない。

Forward開発で残る履歴は、将来コードを起点にするReverse Syncに役立つ可能性がある。これは将来の可能性であり、初期実装の確約ではない。

## 未決事項

- 候補の品質、適合率・再現率、確認時間、探索コストをどう評価するか。
- 履歴だけの場合と比べ、語彙、構造、テストの証拠がどの程度役立つか。
- ノイズをどう判定し、Gitルールだけの場合に対してJevがどの程度改善するか。
- 確認済みの関係を保存・再利用するか。保存する場合、鮮度やrename・分割・統合への追随をどう扱うか。
- branch、PR、mergeの証拠にどのリポジトリホスティング情報を使えるか。また、情報がない場合にどう扱うか。
